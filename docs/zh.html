用一个带认证的控制台管理你所有跑着 DeepSeek Harness 的机器——手机上也能用。每台机器都主动拨出，所以谁都不需要开放入站端口、 不需要公网地址、不用在路由器上打洞。

为什么需要它

dsh web 只绑 loopback 是有意为之

因为它没有任何办法把你和其他能连上这个端口的人区分开。它自己的文档说得很直白：

这道围栏是可达性策略，不是认证；Web 载体不提供任何认证层。

DeepSeek Harness — dsh-client-connection

dsh-fleet 补上这缺的一层，并顺带给你多机视图。它不 fork dsh——节点插件是一个普通的 Cordis 插件，挂在 dsh 本来就设计成传输无关的网关上。

它是怎么拼起来的

一个只搬字节、什么都不解析的控制面

真正本地

每台机器跑自己的 agent。编译、测试、git、语言服务器都在那台机器上、在真实的文件系统上执行。 控制面只做转发，不代替谁执行。

真实的界面

浏览器加载的是那台机器自己的 dsh 界面，经上行通道送达——不是一个复刻品。 dsh 出了新功能，不需要 dsh-fleet 跟着发版。

刻意的不透明

控制面从不解析 dsh 的数据。它搬运帧、关联请求 id、执行自己的访问策略。 正因为它不认识那套接口，dsh 升级不会把它弄坏。

上手

两台机器，五分钟

先起控制面。Docker 是推荐的部署方式。

cp deploy/.env.example deploy/.env    # 改掉两个密码
docker compose -f deploy/docker-compose.yml up -d

注册一台机器，拿到它的一次性 token。

docker compose -f deploy/docker-compose.yml exec dshf \
  dshf node add laptop --label "我的笔记本"

然后在那台机器上装插件，照常启动 dsh web。

dsh plugin --profile web add <节点插件>

export DSH_FLEET_URL=wss://fleet.example.com/uplink
export DSH_FLEET_NODE_ID=laptop
export DSH_FLEET_TOKEN=nt_...

dsh web

没有配置 DSH_FLEET_URL 时插件完全不生效，所以装上它不会改变 dsh web 在那台机器上原本的行为。

部署之前

它目前还不是什么

Pre-alpha，而下面这些缺口属于「事前知道比事后发现好」的那类。

  • 没有 TLS，也没有限流。对外暴露前请在前面放一个终止 TLS 的反向代理；在那之前默认绑定会把它锁在 loopback 上。
  • 一个浏览器同时只驱动一台机器。dsh 客户端用绝对路径寻址 API 和静态资源，所以你进去之后那台机器占据整个 origin。
  • 通信协议有版本号但还不稳定。节点和控制面应当一起升级。
  • 特权方法——凭据、设置、宿主自己的文件对话框——默认拒绝，且每次决定都会记录。
